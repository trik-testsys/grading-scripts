# Проверка решений задач для TrikStudio

Данный проект содержит скрипт для сборки образа docker контейнера 
способного проверять решения задач, 
а также скрипты для взаимодействия с данным образом.

## Зависимости

Для работа с данным проектом, необходимо иметь установленный
[docker](https://docs.docker.com/get-docker/)
и bash. Работоспособность протестирована на linux,
работоспосбность на macos, вероятно потребует минорных изменений.

## Сборка образа

Для сборки образа предназначен скрипт ./build.sh, 
для подробной информации о скрипте:

```bash
./build.sh --help
```

TrikStudio собирается из исходников
[trikset/trik-studio](https://github.com/trikset/trik-studio)
на зафиксированном коммите, поэтому пересборка образа старой версии
скриптов даёт ту же версию TrikStudio.

### Список версий TrikStudio

Версии, для которых собираются образы, перечислены в `versions.txt`:
по строке на версию, в формате `<версия> <SHA коммита trik-studio>`, например

```
2026.3 d7966b8aad0a046dac730360a9ed8a7797738c68
```

Чтобы добавить версию, нужно найти коммит её тэга
(`git ls-remote --tags https://github.com/trikset/trik-studio.git '<версия>*'`,
для аннотированного тэга нужна строка с `^{}`) и добавить строку в `versions.txt`.
CI собирает и тестирует образ для каждой версии из списка,
при публикации релиза все образы отправляются в Docker Hub.
Базовый образ для новой версии собирается и отправляется в Docker Hub
при первом прогоне CI в main (или в релизе).

Минимальная поддерживаемая версия — 2025.4: grade.sh передаёт в 2D-model
опцию `--delay-before-exit`, которой нет в более ранних версиях.

### Образы и тэги

Сборка разделена на два образа:

```
<docker-hub-user>/trik-studio-base:<версия TrikStudio>-<первые 12 символов SHA>  -- TrikStudio
<docker-hub-user>/trik-studio:<версия TrikStudio>-<версия скриптов>             -- TrikStudio + скрипты
```

Базовый образ долго собирается из исходников, поэтому он собирается
один раз на версию и хранится в Docker Hub. `./build.sh` берёт его
локально или скачивает из Docker Hub и собирает из исходников, только если его нигде нет.
Образ для проверки — это базовый образ плюс скрипты из `docker`, он собирается за секунды.

Тэг базового образа зависит только от коммита TrikStudio. Если поменялся
рецепт сборки (`docker/base`), базовые образы нужно пересобрать принудительно:
локально — `./build.sh ... --base build --push-base`, в CI — ручным запуском
workflow тестов с опцией `rebuild-base`. Существующие тэги при этом перезаписываются.

Версия скриптов по умолчанию — `git describe --tags` этого репозитория,
в релизе — тэг релиза (например, `testsystrik/trik-studio:2026.3-v2.3.0`).
Пример сборки:

```bash
./build.sh --trik-studio-version 2026.3 --docker-hub-user testsystrik
```

Далее подробное описание процесса сборки:

``` 
./build.sh [options]
├── Поиск SHA коммита для версии в versions.txt
├── Базовый образ: локальный, из Docker Hub или сборка (docker/base/Dockerfile)
│   ├── Этап builder (ubuntu 22.04), вызов build_trik.sh <версия> <SHA>
│   │   ├── Загрузка исходников trik-studio на коммите (с сабмодулями)
│   │   ├── Установка зависимостей (buildScripts/github/install.sh из trik-studio)
│   │   ├── Сборка без тестов (buildScripts/github/build_internal.sh из trik-studio)
│   │   ├── /TRIKStudio/bin: 2D-model, patcher, trik-studio, библиотеки, плагины
│   │   ├── /TRIKStudio/lib/python-runtime: stdlib Python и numpy
│   │   └── Список apt пакетов, нужных бинарникам во время работы
│   ├── Финальный этап (ubuntu 22.04)
│   │   ├── Установка runtime пакетов, xvfb, ffmpeg
│   │   └── Копирование /TRIKStudio из builder
│   └── С --push-base: отправка собранного базового образа в Docker Hub
├── Образ для проверки (docker/Dockerfile): базовый образ + скрипты из docker
└── Проверка версии TrikStudio в образе с помощью echo_version.sh
```

Сборка TrikStudio занимает десятки минут,
инструменты сборки в итоговый образ не попадают.


## Проврека решений

Для проверки решений предназначен скрипт ./grade.sh, 
для подробной информации о скрипте:

```bash
./grade.sh --help
```

Тестами для решения задачи являются поля для робота, 
артефактом проверки является набор логов (в JSON формате) исполнения на каждом тесте.
Классическим способ оценивания задачи является вывод набранных баллов в лог, 
последущий парсинг и суммирование результатов по тестам. 
Примеры полей можно найти в директории examples/straight_line/fields 

Резульат проверки на поле с именем field.xml именуется field.json.

Проверка выполняется в несколько этапов, 
далее подробное описание процесса сборки:

``` 
./grade.sh [options]
├── Настройка параметров запуска docker образа 
│   ├── Тестируемое решение
│   ├── Директория с полями
│   └── Директория для записи результатов
└── Запуск docker образа 
    ├── Вызов внутреннего grade.sh
    └── Для каждого поля
        ├── Копирование файла решения
        ├── <<Патчинг>> решения с соответствующем полем
        ├── Запуск пропатченного решения
        └── Запись результатов в соответствующею директорию
```
